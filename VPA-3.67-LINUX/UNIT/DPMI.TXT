What is this?

  DPMI for Turbo Pascal, or D4TP for short, is a unit that enables your
  Turbo Pascal programs to use a DPMI server to break the 640k limit.
  It works with Turbo 6 and Turbo 7.

  This file is a rough guide only, for documentation on the individual
  functions see the source code.


What do I need?

  + Turbo Pascal 6 or 7, set to "Compile to disk"
  + a 16-bit DPMI server (RTM, 32RTM, any DOS box) or `dpmi16bi.ovl'
  + DOS 3 or better


How much does it cost?

  Nothing. D4TP is free software. See license at the end of this file.


How does it work?

  When you call `InitDPMI', this unit will check if DPMI is available.
  If possible, it will switch to protected mode and relocate your
  program for protected mode. This is done by opening the .exe file and
  scanning for relocation items. It then patches the runtime library
  and modifies some pointers. When `InitDPMI' returns, your program runs
  in protected mode.

  When you call `InitDPMIOverlay', the same is done with the overlay
  file.

  If protected mode is not accessible, `InitDPMI' will return and your
  program will execute as usual, in real mode.

  Since version 27/Apr/2002, D4TP will attempt to automatically load the
  Borland DOS extender `dpmi16bi.ovl'.

  Note: D4TP assumes that the DPMI server provides an API translator
  for INT 21h (DOS functions). The DPMI specification does not mandate
  this, but all 16-bit DPMI servers known to me do it.


But can't Borland Pascal also compile for protected mode?

  Yes. But Borland Pascal is not Turbo Pascal. And there is no Borland
  Pascal 6. So this unit is one of the few chances for TP 6/TP 7 users
  to use protected mode.

  In addition, for a Borland Pascal program, you have to choose if you
  want them to run in protected mode at compile time. Our programs decide
  this at run-time. And, our programs have the advantage that every
  procedure/variable (except for overlay procedures) also has a real-mode
  address. Our stack and data segment completely lies in real-mode
  address space which vastly simplifies communication to real-mode
  programs.


When should I call `InitDPMI'?

  As early as possible. In theory, you can call `InitDPMI' any time you
  want, but then you'd have to translate all pointers you obtained before
  into protected mode pointers. That task isn't fun. In addition, you
  can't `FreeMem' memory in protected mode you `GetMem'd in real mode,
  and translating `GetMem'd pointers is not yet directly supported (though
  easily possible). If you need to translate pointers, use the
  `TranslateXXX' functions.

  You must not have called `OvrInit' before `InitDPMIOverlay'. We need
  the virgin overlay manager's data structures.


What pointers do I need to translate?

  Those which do not have a relocation item in the .exe file. In short,
  everything you assigned with actual Pascal code, before calling
  `InitDPMI'. Typed constants need no translation, neither need pointer
  literals in your code. All pointers you generate after `InitDPMI' need
  no translation. In fact, it'll be very hard to generate real-mode
  pointers in DPMI mode.


What is this `SysExt' thing?

  Declarations of which I prefer they were in the `System' unit. Under
  Borland Pascal, most of them are (except for the `_DPMI' variable).
  This is just a stylistic issue, there would be no problem moving them
  elsewhere, for example into the DPMI unit itself.


What code do I need to port?

  + code which accesses real mode memory: you can no longer play with
    segment addresses, e.g., Mem[0:$417] is completely different from
    Mem[$40:$17]. For the most-frequently used segments, this unit offers
    standard selectors (Seg0040, SegA000, SegB000, SegB800). The real
    mode values of DS and SS are available in `_realds' and `_realss'.
  + code which invokes interrupts with real-mode buffers: when running
    in protected mode, you need to set up a transfer buffer, and invoke
    the interrupt manually through `DPMIInvokeRealmodeInterrupt' (note
    that this function must be called from an ASM block as it takes its
    parameters in registers). Code which only invokes interrupts with
    values in the general-purpose registers need not be ported; DPMI
    hosts are required to reflect those interrupts to real mode. If your
    buffer is in the data or stack segment, you can pass `_realds' or
    `_realss' as the segment register value to `DPMIInvokeRealmode-
    Interrupt'.
  + everything related to manipulating interrupts. `SwapVectors' must not
    be used in protected mode. `GetIntVec' and `SetIntVec' can be
    replaced by `DPMIGetRealmodeInt' and `DPMISetRealmodeInt' (see
    next section), or any other subfunction of INT 31/AH=02.

  Note that *you* must write the code that decides whether to call
  `DPMIInvokeRealmodeInterrupt' or directly issue a `int' instruction.
  The `DPMIxxx' functions are pure wrappers for DPMI API calls and
  do not emulate them in real mode.


I have this function which must be executed in real-mode (an interrupt
handler, probably).

  No problem. Call `DeclareRealmodeProcedure' before calling `InitDPMI'.
  `DeclareRealmodeProcedure' expects a pointer to the procedure, and a
  pointer to the next procedure after it. For example, if you have

          PROCEDURE KeyboardInterrupt; ASSEMBLER;
          ASM
                { interrupt code here }
          END;

          PROCEDURE MyProcedure;
          ...

  you call `DeclareRealmodeProcedure(@KeyboardInterrupt, @MyProcedure)'
  before `InitDPMI'. `DeclareRealmodeProcedure' does not work with overlay
  functions. There is a limit of 10 real mode procedures
  (DPMI_MAX_RM_PROCS). If you need more, increase that limit. Your program
  will crash with an appropriate message if you need to do this.

  Note that real mode procedures must not call most of the standard library
  functions (which expect protected mode).

  To set a real-mode interrupt handler, use `DPMISetRealmodeInt'.
  `DPMISetRealmodeInt' requires three parameters:
  + the interrupt number
  + the pointer to the procedure
  + a boolean value: if TRUE, the pointer is a real-mode pointer, as
    obtained with `DPMIGetRealmodeInt'. If FALSE, it is a pointer to a
    procedure you obtained with the `Addr' function or `@' operator.
  Typical use is
      DPMIGetRealmodeInt($09, OldKeyboardInt);
      DPMISetRealmodeInt($09, @KeyboardInterrupt, FALSE);
      { your program here }
      DPMISetRealmodeInt($09, OldKeyboardInt, TRUE);


So, after all this red-tape I have to do, what are my advantages?

  + you can access much more memory: a 16-bit-only DPMI server can make
    up to 16 meg available to your program. This unit has no problem with
    a DPMI server which offers even more (though an original 286 can only
    address 16M). I have already seen a D4TP program allocate 20 meg;
  + limited protection: references to uninitialized or NIL pointers are
    detected (GPF, runtime error 216);
  + faster operation for overlaid programs: no need to swap in/out code
    all the time;
  + can create core dumps for post-mortem diagnosis.


And the disadvantages?

  + need porting some code;
  + possibly slower start-up time because the overlay is loaded into
    memory at start-up, not on demand;
  + need an external DPMI server or the `dpmi16bi.ovl' overlay.


Are there any other differences between real mode and protected mode?

  + memory allocation has different semantics. Returned pointers can have
    offset addresses other than 0 and 8. `MemAvail' and `MaxAvail' are
    different (your program may start with `MemAvail = 0'!). See the
    section on memory allocation below. The `HeapError' hook is not called
    when D4TP increases its memory pool;
  + you'll get different errors in real mode and protected mode. In real
    mode, accessing a drive without a disk gets error 152, in protected
    mode it gets error 3 due to a simpler error handler implementation;
  + HeapPtr and HeapEnd are set to NIL to detect programs playing with
    the heap. Use this fact to your advantage (allows DPMI detection without
    actually including this unit or SysExt);
  + the #GP/#SF exceptions generate an error 216. However, the address
    in `ErrorAddr' is completely worthless (it points to the `Exception'
    procedure in the DPMI unit). Note that this is different than Borland
    Pascal which generates error 202 on an #SF. I believe that 202 has
    a different semantics than #SF (202 is for software-detected stack
    overflows -- and if your program does not catch stack overflows in
    software ($S+), it by definition contains no stack overflows);
  + error addresses are generally unusable, but see the comment on
    `DPMIDumpSegmentAssignments';
  + the CRT unit can't be used. It installs an interrupt handler for
    Ctrl-Break, so your program crashes when a user hits Ctrl-Break.
    Except for that, it should work under TP 7 (partly under TP 6 with
    `DirectVideo' set to FALSE);
  + the Graph unit can't be used (accesses video memory, loads files into
    heap and executes them);
  + floating-point emulation is not possible. This unit does not support
    the Turbo Pascal emulator. I assume that the DPMI host provides
    emulation if needed;
  + Ctrl-Break is ignored. This unit is intended for interactive programs ;)


How do I debug my DPMI program?

  The Turbo Pascal debugger will not work with DPMI programs. Actually,
  it gives up long before you consider using DPMI to get more memory ;-)

  First, spicing your program with `Write's greatly helps.

  Second, the function `DPMIDumpCore' can be used to produce core dumps.
  This only works in protected mode. A core dump contains all the data
  segments of your program, plus some meta-information which can be used
  to inspect the program. You can call that function anytime you want.
  `DPMIDumpCore' expects a DOS file handle as its argument; alternatively
  use `DPMIDumpCoreFile' which expects an opened FILE.
     IF _DPMI THEN BEGIN
       Assign(F, 'coredump');
       Rewrite(F);
       DPMIDumpCoreFile(F);
       Close(F);
     END;
  Core dumps will usually be at least 256k.

  If your program crashes, you can use the usual `ExitProc' method to
  hook into runtime errors, and call `DPMIDumpCore' from there -- this is
  what I do in PCC.

  The `coredb.pl' Perl program can then be used to examine the core dump.
  The comments at the beginning contain usage instructions. The `sympriv.pl'
  script can be used to make MAP files (which the core debugger needs)
  contain more symbols.


This sounds very complicated. Is porting for DPMI really *that* difficult?

  No. I ported Planets Command Center (http://www.inf.tu-dresden.de/~sr21/
  pcc.html, a huge graphical application) in about a week. PCC does neither
  use the Graph unit, nor the CRT unit (hence I didn't bother supporting
  them). Porting the PCC graphics code mainly meant loading segment values
  from variables, not constants (a good idea anyway), and using
  `DPMIInvokeRealmodeInterrupt' for some VESA stuff. Just about anything
  else could be taken over verbatim.

  If the program originally is for BP7 DPMI, it's even easier. Porting
  VPA (http://vpa.sourceforge.net/) needed only adding the initialisation
  code and turning of 8087 floating point (read, half-an-hour in total).


How does memory allocation work?

  Memory is allocated from the DPMI server in blocks of 64k. `GetMem',
  `New' and so on do then sub-allocate from that. This way, `MaxAvail'
  will never return more than 64k.

  It is generally not possible to provide a reliable `MemAvail' or
  `MaxAvail' function. DPMI has a function to retrieve information about
  free memory. But when DPMI is used in a multi-tasking environment,
  another process may grab the memory between you querying the free
  memory and trying to allocate it. However, a common idiom in Turbo
  Pascal is
    IF MaxAvail < SIZE THEN Error ELSE GetMem(p, SIZE);
  (note that this idiom does not always work with BP7 in protected mode!)
  So this unit chooses a different approach: when you call `MaxAvail',
  D4TP checks the maximum free size, like you expect. But if that size
  is less than 64k-8, and the `df_HeapPrealloc' bit in `DPMIFlags' is
  set (default), it allocates a fresh 64k segment. This way, the above
  construction will work perfectly: it's guaranteed that `MaxAvail' bytes
  can always be allocated. No such trick is done for `MemAvail'.
  `MemAvail' has no real use in production code other than being displayed
  in `About' dialogs, so it will return only the amount of memory
  currently free in D4TP's memory pool, not the amount of total free
  memory -- which were worthless anyway.

  You can use the variable `DPMIBlocksUsed' to check how many 64k
  blocks are currently under D4TP's control.


I converted my program, and it now crashes. What gives?

  "DPMI: fatal error -- ABORT"
    a) During initialisation of protected mode, D4TP encountered an error.
    It is too late to return to real mode, but too early to continue
    in protected mode. This is a message equivalent to "<program> not
    executable" from command.com.
    b) You fed a pointer into `TranslateXXX' which violates some
    constraints. The `TranslateXXX' functions only accept pointers into
    your program, as the `Addr' or `@' operator gives you. You can not
    translate "normalized" pointers or pointers to real-mode memory
    this way; use the `DPMISegmentToXXX' Functions if you have to.
    c) `DPMISegmentToXXXX' ran out of selectors. Never seen that one.

  "DPMI: too many segments in executable -- ABORT"
    You have a real big program. Increase DPMI_MAX_SEGMENTS.

  "DPMI: too many real-mode procedures"
    Increase DPMI_MAX_RM_PROCS.

  The last two are "deterministic" in the sense that if you don't get
  them, your users will also never see them.


I have DPMI, but my program won't use it!

  "DPMI: Not enough memory to initialize DPMI"
    D4TP failed to allocate the memory requested by the DPMI host for
    its internal use. Never seen that one.

  "DPMI: can't open executable"
  "DPMI: executable file damaged"
    D4TP could not open the .exe file to read the relocations. May happen
    with "execute only" files on Netware.

  "Can't handle 16 bit apps, sorry"
    You can not use the CWSDPMI server with D4TP.


Where do I get a DPMI server?

  D4TP can load `dpmi16bi.ovl'. That file can be downloaded from Garbo:
    ftp://garbo.uwasa.fi/pc/turbspec/newrtm.zip
    ftp://ftp.tu-chemnitz.de/pub/garbo/turbspec/newrtm.zip
  `InitDPMI' will automatically load that file when it finds it in the
  same directory as your program's .exe file, or in the current directory
  (Borland Pascal apps will also look along the %PATH%, D4TP does not do
  that (yet)).

  If you do not have that file, you can still use the old method: load
  the DPMI server manually.

  Windows
    automatically provides DPMI in DOS boxes

  DOS
    a) use `rtmres' from Borland Pascal:
         set rtm=extleave 8192         # leave 8 MB for D4TP
         rtmres yourprogram
    b) use `32rtm' from Borland C++ (you find this with various BC++
    programs on the Net):
         32rtm                         # load extender
         yourprogram
         32rtm -u                      # unload

  OS/2
    D4TP programs require "DPMI_DOS_API=ENABLED" in the DOS session
    properties.

  Linux
    set `$_dpmi = (8192)' in /etc/dosemu.conf, give your user all
    privileges (`youruser c_all' in /etc/dosemu.users), and
    `chmod 666 /dev/zero'.

  To prevent use of an active DPMI server at runtime, set the environment
  variable `DPMI' to `NO'.


I don't like <this-and-that> in this unit!

  I wrote this unit for one particular purpose (the Planets Command
  Center). The interface of D4TP was designed to exactly fit the needs
  of that program, nothing more, nothing less. I know this may not
  match your needs. So if you don't like something -- change it.
